**Key Fuzzy Token Plan**

This document is intended to be a central planning and feature document for the basis blended tokens method.

**Preliminaries**

This feature is planned for implemenation into the cotorra EHR generative event model training pipeline. This pipeline is built to train on collated, tokenized, and winnowed timelines generated by the cocoa library.

A modifid version of the cocoa library is available at ~/new_cocoa.

**Key changes to cocoa**

The most important change to cocoa is the addition of a new column **exact_ranks**. Alongside tokens and times, this tracks the exact within category numerical rank (in [0,1]) for each numerical token recorded.

This new information is key to the plannd basis blended tokens mehod.

> **Note (verified against `~/new_cocoa`):** this cocoa-side work is already
> done. `Tokenizer` (`src/cocoa/tokenizer.py`) already ships an
> `include_exact_rank` config flag that computes `exact_rank` via
> `_add_exact_rank` (empirical CDF midpoint, `(p1+p2)/2`, per code) and emits
> it as the `exact_ranks` list column in `tokens_times.parquet`. `Winnower`
> (`src/cocoa/winnower.py:112-119`) already carries it through inference as
> `exact_ranks_past`, with a comment explicitly anticipating "a
> `use_exact_rank` model" and a `NumericalBasisModel` — i.e. this exact
> feature. **No cocoa changes are required.** The only requirement on the
> cocoa config is `fused: true` (already the default) and
> `include_exact_rank: true`; `n_bins` can be anything (see "Cocoa
> prerequisites" below — its value stops mattering once cotorra collapses the
> vocab). One real dataset already has all of this: `updated_absolute_centiles/`
> (n_bins=100, fused=true, include_numeric_values=true) has a populated
> `exact_ranks` column and is a good smoke-test target — see "Testing &
> validation" below. (Its `tokenizer.yaml` `cfg` block is oddly missing
> `include_exact_rank: true` even though the column exists in the parquet —
> looks like a stale/hand-run artifact, not a bug to chase; just don't rely on
> that particular `tokenizer.yaml`'s `cfg` for `include_exact_rank`, trust the
> parquet schema instead, or retokenize.)

**Core method**

The primary flow of the basis blended tokens method is the following pipeline.

Hyperparameters: k. k is the number basis elements per numerical category. The basis elements are elaborated on below

Basis element: (e_i, P_i). Each basis element consists of two primary components. Each numerical category has a unique set of k basis elements.

First, an embedding e_i (of the same dimension of the token embeddings for the cotorra trainsformer).

Second, a probability distribution P_i which is a continuous PDF over the support [0,1]. In this first implementation, P_i will always be a beta distribution with parameters alpha_i and beta_i.
For the model, we save log(alpha_i) and log(beta_i) as parameters (these will sometimes be trainable and sometimes be frozen depending on the config).

> **Note:** "numerical category" = a cocoa `code` that has numeric values,
> i.e. exactly the categories that `Loss.quantile_token_loss` already infers
> today by parsing `<code>_Q<bin>` vocab labels (`src/cotorra/loss.py:44-64`,
> fused mode only). Same definition, reused. k is a single global
> hyperparameter — the *count* is shared across all categories, only the
> learned (e, alpha, beta) values differ per category, per the text above.

**Initialization of a basis element**

e_i should be randomly initialized in the same way as all the other transformer embeddings.

P_i should be initialized according to the ith order statistic of the Uniform r.v. over [0,1] with k total draws. i.e., for 1<=i<=k, Beta(i,k+1-i). In other words, log(alpha_i) =log(i) log(beta_i) = log(k+1-i).

> **Note:** the "randomly initialized the same way as all the other
> transformer embeddings" requirement is satisfied *for free*, not by special
> constructor code, by making each (c, i) a literal row of the model's own
> `nn.Embedding` (see "Design decisions" below) — the base HF model's own
> init (e.g. Llama's `normal_(std=initializer_range)`) already touches every
> vocab row uniformly. In 0-indexed code (i = 0..k-1), init is
> `log_alpha[:, i] = log(i + 1)`, `log_beta[:, i] = log(k - i)`; identical
> across categories at init time, but each category keeps independent
> parameter storage so they can diverge once training starts (if trainable).

**Determination of mixture weights**

For any given rank in [0,1] and any given basis set, we define the following method for computing a set of k **mixture weights**.

For a given numeric category c, define f(r, i) = P_i(r). In other words, f, for each i, gives the density at r.

To obtain k mixture weights, we define w_i = f(r,i)/(sum over all i: f(r,i)). This ensures we have a valid set of mixture weights that sum to 1.0.

Thus, for any numerical category c and rank r, we obtain a unique set of mixture weights {w_1,...,w_k}.

> **Note:** implemented as a log-space softmax
> (`w = softmax(log_pdf(r; alpha, beta), dim=basis)`) rather than a raw
> ratio, for numerical stability — see "Numerical stability" below. At init
> (alpha, beta >= 1 for every i) the Beta pdf is finite everywhere on [0,1],
> but if alpha/beta are trainable they can drift below 1, which makes the pdf
> diverge at the r=0/r=1 boundary; ranks get clamped away from the exact
> boundary before evaluating the pdf to avoid inf/nan.
>
> **Extension (post-validation):** a trained per-category, per-basis
> *importance scale* `a_c,i` generalizes this to
> `w_c,i = a_c,i * f(r,i) / sum_j a_c,j * f(r,j)`, letting the model learn
> each basis element's overall influence independently of its Beta shape.
> Parameterized as `log(a_c,i)`, added to `log_pdf` before the same softmax
> (`softmax(x)_i = exp(x_i)/sum_j exp(x_j)` with `x = log(a) + log_pdf` is
> exactly this ratio), initialized to `log(a)=0` (`a=1` uniformly) so it
> reproduces the original unscaled formula until training moves it. Gated by
> `basis_blended_tokens.train_importance_scale` (default `true`),
> independent of `train_beta_params`. Added after the first full-data
> validation run showed the base method (k=8) modestly but consistently
> outperforming standard tokenization; being tried alongside a larger
> `k=20` to see whether either or both push the gap further.

**Use of mixture weights**

Mixture weights determine both the embedding and loss for numeric value entries (which are represented by category and rank).

**Input embedding**: Using e_i and w_i described above, the embedding for some entry (c, r) will be embedded by: sum over i from 1 to k: w_c,i(r) * e_c,i

**Loss function**: Since we do not have a single token defining (c,r), we instead compute our next token prediction loss in the following way:

Modified token vocabulary: Rather than the fused binned numeric tokenization vocabulary natively supported by cocoa, we implicitly redefine the vocabulary in the following way.

Standard cocoa: vocab_size = num_non_numeric_tokens + (num_of_numeric_categories * num_bins_per_category): Numeric entries are defined by category x bin index

Basis blended tokens: vocab_size =  num_non_numeric_tokens + (num_of_numeric_categories * k): Each numeric category gets k tokens. Real measurements are treated as a blend of these k tokens with the blend mix determined by the rank of the entry.

The additional difference is that we represent numerical tokens as a blend of multiple tokens rather than just one token.

In addition to embedding as described above, we replace one-hot loss targets with the mixture weights described above. The below illustrative example should clarify this concept.

Standard NTP: (c,r) = (Heart rate, 0.47) -> Tokenized using decile bins as heart_rate_Q4 -> Ground truth distribution for CE loss: P(All other tokens) = 0, P(heart_rate_Q4) =1.0

Basis blended tokens: (c,r)  -> Extract mixture weights w_i -> Ground truth distribution for CE loss: P(All tokens of other category and non numeric) = 0, P(c: category, i: basis element index) = w_c,i

> **Note:** this new, smaller vocab is a **cotorra-level** construct — cocoa's
> own tokenizer vocab / `n_bins` is untouched; cotorra collapses the cocoa
> vocab down to `num_non_numeric_tokens + num_categories * k` at
> train/extract time and never writes it back into cocoa's `tokenizer.yaml`.
> See "The collapsed basis vocabulary" below for exactly how.

**Additional Clarification Regarding Embedding Ties**

It is very important for this method to maintain the tie between embeddings in the input layer and the conversion to vocab logits.

What this means in practice: The e_i used to generate the blended input embeddings must be the same e_i used to generate logits for the vocab token (c,i)=(c: category, i: basis element index). To further clarify this point, here are the equations below.

Given input (c,r), e(c,r) = sum for all i 1 to k, w_c,i(r) * e_c,i

To obtain logit of e_c,i: h^T @ e_c,i

This tie is a key design decision and must be maintained. Without this tie, the output side risks distributional collapse. Since the model can decide to always predict a specific basis element, the model can also decide to assign all entries to the same basis element and achieve perfect accuracy.
With the tie, the input embeddig encourages the embeddings to separate as they are more useful for the prediction of other tokens when distinct tokens are embedded distinctly.

> **Note:** the plan below gets this tie "for free" and structurally
> guaranteed (not by convention/care) — (c, i) are real rows of the base HF
> model's own embedding matrix, `tie_word_embeddings=True` is forced on that
> base model, and the blended input embedding is built by reading *from that
> same matrix*. There is no separate parameter set for the output side to
> drift out of sync with. See "Why the tie is structurally guaranteed" below.

**Summary of parameters**
log(alpha_c,i), log(beta_c,i) - k for each numerical category. These should be saved with the final model and wired to receive gradient.
e_c,i                         - k for each numerical category. Remember the tie.

**Important reminders**
These features should work along with the time based ROPE. These features must work for all steps of the model (aside from generative scoring). This means that these features should be possible to enable for training/tuning and then loaded faithfully from the pretrained model for extraction or any other downstream tasks.

# Implementation Plan

## 0. Status

Planning only — nothing below is implemented yet. This section is the
detailed design; questions that materially changed the shape of the plan were
already asked and answered (see "Locked-in design decisions"). Anything still
open is called out explicitly under "Known gaps / open follow-ups" rather than
guessed at.

## 1. Locked-in design decisions

These were confirmed with the user and drive everything below:

1. **Loss interaction**: `basis_blended_tokens` is kept *independent* of
   `quantile_token_loss` and the broken `was_token_loss` stub
   (`src/cotorra/loss.py`, added in commit `1193c9f`, calls
   `self.was_token_loss` which doesn't exist and reads
   `self.cfg.was_tokenLoss` — a typo for `was_token_loss`). No blocking
   validation error is added if a user combines them. The stub is left as-is
   — **not** fixed or removed as part of this work. See "Known gaps" for what
   "independent" does *not* currently mean (it doesn't mean the combination
   is functional out of the box).
2. **Model wiring**: a custom HF `PreTrainedModel` / `PretrainedConfig`
   subclass owns the collapsed vocab mapping, `k`, and the frozen/trainable
   flag, so `save_pretrained` / `from_pretrained` round-trip everything
   automatically (matches "loaded faithfully from the pretrained model").
3. **alpha/beta freeze granularity**: one global boolean
   (`basis_blended_tokens.train_beta_params`) for all categories — no
   per-category override in v1.
4. **generative-score**: no explicit guard/error. Documented as unsupported
   (README + recipe), not enforced in code. In practice it will fail loudly
   anyway — `GenerativeScorer`'s sglang/`quick_sco_re` engine loads a
   standard HF checkpoint shape and has no notion of our custom model class
   or collapsed vocab.

## 3. The collapsed basis vocabulary

A new helper, `build_basis_vocab(tkzr_cfg, k)` in the new
`src/cotorra/basis_blended.py` (see below), is the **single source of
truth** for the cocoa-vocab -> basis-vocab mapping. It's called once in
`Trainer.__init__`, and the *same* resulting object is threaded to both
`model_init` (so the model's embedding table matches) and `Loss` (so loss
targets use the same category/id assignment as the model) — no duplicate
derivation anywhere.

Construction (reuses `Loss.quantile_token_loss`'s existing category-parsing
approach, `src/cotorra/loss.py:44-53`, rather than inventing a new one):

1. Load `tkzr_cfg.lookup` (cocoa's `tokenizer.yaml`). Build `q_type`, the
   mask of vocab labels ending in `Q{i}` for `i in range(n_bins)`, and
   `qt_cats` via `rsplit(label, "Q", maxsplit=1)` — identical to today's
   `Loss` code. `categories = sorted(unique(qt_cats))` (e.g.
   `"VTL//heart_rate_"`, `"AGE//age_"`, trailing separator included, matching
   `rsplit`'s output).
2. Non-numeric tokens (everything not matched above, including `UNK`, `BOS`,
   `EOS`) keep a 1:1 remap to new sequential ids `0..num_non_numeric-1`,
   preserving relative order from the original lookup.
3. Each category `c` gets a contiguous block of `k` new ids. Label them
   `f"{c}Q{i}"` for `i in 0..k-1` — i.e. the *same* `_Q<n>` naming
   convention as cocoa's bin tokens, just with `k` slots instead of
   `n_bins`. (Deliberate: keeps the vocab human-readable and leaves the door
   open for `quantile_token_loss`-style parsing to work against this vocab
   later — see "Known gaps".)
4. Emit:
   - `vocab_size = num_non_numeric + len(categories) * k`
   - `lookup: dict[str, int]` — the full new label -> id map
   - `category_base_id: list[int]` (len = num categories) — collapsed id of
     each category's basis element 0
   - `raw_to_category: list[int]` (len = original cocoa vocab size) —
     category index, or `-1` for non-numeric tokens
   - `raw_to_collapsed: list[int]` (len = original cocoa vocab size) — the
     new collapsed id every raw token id remaps to. Non-numeric: its real new
     id. Numeric: `category_base_id[cat]` — an arbitrary-but-deterministic
     placeholder (see next paragraph).
   - `bos_token_id`, `eos_token_id` in collapsed space

**Why numeric positions get a placeholder id, not "the right" id:** there is
no single collapsed-vocab id that correctly represents a continuous `(c, r)`
pair — that's the entire premise of the method. `raw_to_collapsed` exists so
`input_ids`/`labels` tensors stay ordinary same-shaped integer tensors (which
several bits of code — padding, dataset schemas — expect), but its value at a
numeric position is never actually read by the embedding lookup (blending
overrides it) or by the loss (which uses `category_ids`/`ranks`, not the
placeholder id, for numeric positions). It only matters as a well-defined
fallback for anything that *doesn't* know about basis blending — see
"`generate()` and hard-token fallback" below, where this fallback turns out
to be exactly the right behavior, not a hack.

## 4. New module: `src/cotorra/basis_blended.py`

### 4.1 `BasisBlendedConfig(PretrainedConfig)`

Composite config (same pattern HF uses for `EncoderDecoderConfig`): stores
the *inner* base model's config as a plain dict (`base_model_type`,
`base_config: dict`) plus everything `build_basis_vocab` produced (`k`,
`train_beta_params`, `categories`, `category_base_id`, `raw_to_category`,
`raw_to_collapsed`, `vocab_size`, `bos_token_id`, `eos_token_id`). All fields
are plain ints/strs/lists/dicts, so standard `PretrainedConfig`
JSON (de)serialization handles it with no custom `to_dict`/`from_dict`
needed. List sizes are small (cocoa vocab is ~1.3k tokens per
`CLAUDE.md`), so embedding `raw_to_category`/`raw_to_collapsed` directly in
`config.json` is cheap.

Registered at import time:

```python
AutoConfig.register("basis_blended", BasisBlendedConfig)
AutoModelForCausalLM.register(BasisBlendedConfig, BasisBlendedCausalLM)
```

This is what makes extraction need **zero changes** to its model-loading
line (`AutoModelForCausalLM.from_pretrained(self.model_home)` in
`extractor.py:52`) — HF's Auto* dispatch picks the right class from
`config.json`'s `model_type` automatically, as long as
`cotorra.basis_blended` has been imported somewhere first (import it eagerly
in `cotorra/__init__.py`, or lazily at the top of `trainer.py`/`extractor.py`
— either works, just needs to happen before `from_pretrained`/`from_config`
is called).

### 4.2 `BasisBlendedCausalLM(PreTrainedModel)`

```
config_class = BasisBlendedConfig

__init__(config):
    inner_cfg = AutoConfig.for_model(config.base_model_type, **config.base_config)
    inner_cfg.vocab_size = config.vocab_size          # collapsed size
    inner_cfg.tie_word_embeddings = True               # forced, see below
    inner_cfg.bos_token_id, inner_cfg.eos_token_id = config.bos_token_id, config.eos_token_id
    self.base_model = AutoModelForCausalLM.from_config(inner_cfg)

    n_cat, k = len(config.categories), config.k
    log_alpha0 = log(arange(1, k+1))            # shape (k,), order-statistic init
    log_beta0  = log(arange(k, 0, -1))          # shape (k,)
    self.log_alpha = nn.Parameter(log_alpha0.expand(n_cat, k).clone(),
                                   requires_grad=config.train_beta_params)
    self.log_beta  = nn.Parameter(log_beta0.expand(n_cat, k).clone(),
                                   requires_grad=config.train_beta_params)
    self.register_buffer("category_base_id", tensor(config.category_base_id))

get_input_embeddings / set_input_embeddings / get_output_embeddings /
set_output_embeddings: delegate to self.base_model's (needed for HF's
generate()/resize_token_embeddings plumbing; forward() also uses these).

forward(input_ids, category_ids, ranks, position_ids=None, attention_mask=None,
        output_hidden_states=False, **kwargs):
    embed = self.get_input_embeddings()
    base_embeds = embed(input_ids)                       # (B,T,H) fallback / non-numeric
    numeric = category_ids >= 0                           # (B,T) bool
    if numeric.any():
        cat = category_ids.clamp(min=0)
        a = self.log_alpha[cat].exp()                     # (B,T,k)
        b = self.log_beta[cat].exp()                       # (B,T,k)
        r = ranks.clamp(EPS, 1 - EPS).unsqueeze(-1)         # (B,T,1)
        log_pdf = (a - 1) * r.log() + (b - 1) * (1 - r).log() \
                  - (lgamma(a) + lgamma(b) - lgamma(a + b))  # (B,T,k)
        w = softmax(log_pdf, dim=-1)                        # (B,T,k) mixture weights
        basis_ids = self.category_base_id[cat].unsqueeze(-1) + arange(k)  # (B,T,k)
        basis_embeds = embed(basis_ids)                     # (B,T,k,H)
        blended = (w.unsqueeze(-1) * basis_embeds).sum(dim=2)
        base_embeds = where(numeric.unsqueeze(-1), blended, base_embeds)
    else:
        w = None
    outputs = self.base_model(inputs_embeds=base_embeds, position_ids=position_ids,
                               attention_mask=attention_mask,
                               output_hidden_states=output_hidden_states, **kwargs)
    outputs["mixture_weights"] = w   # (B,T,k) or None — see Loss section
    return outputs
```

Key points:

- `labels` are deliberately **not** passed into `self.base_model(...)` — loss
  stays externally computed by `TrainerWithCustomLoss.compute_loss`, exactly
  like today's `x_ent_loss`/`label_weighted_loss`, just with two extra
  tensors threaded through (see "Trainer & Loss changes").
- `mixture_weights` is computed once, for every position (not just "input"
  positions), and returned on the output object. The loss re-shifts and
  reuses this *exact same tensor* rather than recomputing `w` from
  `log_alpha`/`log_beta` a second time — see "Why loss reuses `w` instead of
  recomputing it" below. This also sidesteps having to hand `log_alpha`/
  `log_beta` into `Loss` at all (which would otherwise need special-casing
  under Opacus's `GradSampleModule` wrapping — see DP notes).
- Manual log-Beta-pdf (via `lgamma`) rather than `torch.distributions.Beta`
  — equivalent and fully differentiable either way; manual avoids
  constructing a distribution object per forward call. Either is fine; this
  is an implementation-detail choice, not a design one.

### 4.3 Why the tie is structurally guaranteed

`(c, i)` are literal rows of `self.base_model.get_input_embeddings().weight`.
`inner_cfg.tie_word_embeddings = True` means `self.base_model`'s own
`lm_head` reads logits from that *same* weight matrix (standard HF tying,
happens inside `self.base_model`'s own `post_init()` — the outer wrapper
doesn't need to implement its own `tie_weights()`, since it never introduces
a second embedding/head outside `self.base_model`). Blending in `forward()`
reads `embed(basis_ids)` from the identical matrix. There is no code path by
which the input-side and output-side `e_c,i` could diverge — good, this is
exactly what the doc's "Additional Clarification Regarding Embedding Ties"
section is worried about, and it's solved by construction rather than by
discipline.

**Requirement this creates:** `model_args.tie_word_embeddings` must not be
explicitly set to `false` in a `basis_blended_tokens` run — `model_init`
should assert/override this rather than silently trusting a user config
value, since a silent `tie_word_embeddings: false` would quietly break the
method's central correctness property.

### 4.4 `generate()` and the hard-token fallback

HF's `.generate()` loop (used by `Logger.summarize_trained_model` for sample
printouts after training) has no knowledge of `category_ids`/`ranks` and
won't pass them. `forward()` needs a sane default when they're absent:
default `category_ids` to all `-1`. That makes every position take the
`base_embeds = embed(input_ids)` fallback path — i.e. previously-generated
basis tokens (which are real, valid vocab ids like any other) get looked up
as ordinary one-hot embeddings, and generation produces one discrete basis
token per numeric step (a coherent sample from the k pseudo-quantiles, just
not a reconstructed continuous value). This is expected/intentional, not a
bug — it's *also* exactly why plain `.generate()`-based paths don't need to
be part of "generative scoring is out of scope": they degrade gracefully on
their own. `Logger.summarize_trained_model`'s `reverse` dict also needs to be
built from the *collapsed* lookup when this mode is active — currently it's
built from `self.tkzr_cfg.lookup` in three separate places (`trainer.py`,
`tuner.py`, `trainer_dp.py`, all duplicated). Worth collapsing into one
`Trainer`-level property (`self.reverse_lookup`, `self.bos_token_id`) that
picks collapsed-vs-raw once, so `Tuner`/`TrainerDP` inherit the fix instead
of needing three separate patches.

## 6. `Trainer` changes

**`model_init`**: when `"basis_blended_tokens" in self.cfg`, call
`build_basis_vocab(self.tkzr_cfg, self.cfg.basis_blended_tokens.k)` once,
force `tie_word_embeddings=True`, construct `BasisBlendedConfig` +
`BasisBlendedCausalLM` instead of the current `AutoConfig` +
`AutoModelForCausalLM.from_config` path. Store the basis-vocab object on
`self` so `Loss` construction (right below it in `__init__`) can reuse it.

**`collate_fn`**: additionally build, when active:

- `category_ids = raw_to_category_tensor[input_ids]`
- `ranks` = the batch's `exact_ranks` tensor (already [0,1]-scaled by cocoa,
  0.0 placeholder at non-numeric positions — same convention cocoa already
  uses for the padding value, see `tokenizer.py:349-354`)
- `input_ids` / `labels` get remapped through `raw_to_collapsed_tensor`
  before being returned, since the model's embedding table is sized for the
  collapsed vocab only — every id reaching the model must already be in
  collapsed space.

Composes with `time_based_rope`'s existing `position_ids` branch
unconditionally (independent `if` blocks — the doc requires both work
together).

**`TrainerWithCustomLoss.compute_loss`**: needs to forward `category_ids`/
`ranks` from `inputs` into `compute_loss_func` as extra kwargs. Every
existing `Loss` method already accepts `**kwargs`
(`custom_loss(self, outputs, labels, **kwargs)` and friends), so this is a
small, additive change — no existing loss function needs to change
signature.

## 7. `Loss` changes

New `Loss.basis_blended_token_loss(self, outputs, labels, category_ids=None,
ranks=None, **kwargs)`:

```
shift_logits = outputs.logits[:, :-1]        # (B,T-1,V_collapsed)
shift_labels = labels[:, 1:]
shift_cat     = category_ids[:, 1:]
shift_w       = outputs["mixture_weights"][:, 1:]   # (B,T-1,k) — see below

log_probs = log_softmax(shift_logits, dim=-1)
numeric = shift_cat >= 0

# non-numeric positions: ordinary one-hot CE, reusing log_probs (no second softmax)
nonnum_loss = -log_probs[~numeric].gather(-1, shift_labels[~numeric,None]).sum()

# numeric positions: soft CE against the mixture-weight target
basis_ids = category_base_id[shift_cat[numeric]][:,None] + arange(k)   # (N,k)
log_probs_numeric = log_probs[numeric].gather(-1, basis_ids)            # (N,k)
numeric_loss = -(shift_w[numeric] * log_probs_numeric).sum()

return nonnum_loss + numeric_loss   # sum-reduced, matches the repo's Aug-10
                                     # move to summed (not mean) reduction
```

**Why loss reuses `outputs["mixture_weights"]` instead of recomputing it
from `log_alpha`/`log_beta`:** `Loss` doesn't otherwise hold a reference to
the model (only `cfg`/`tkzr_cfg`), and `model` in a DP run is wrapped in
Opacus's `GradSampleModule`, which would need `model._module.log_alpha`-style
unwrapping (`trainer_dp.py` already has this pattern via
`_unwrapped_model()`) just to read the parameter. Reusing the tensor the
model already computed sidesteps that entirely, guarantees the loss target
and the embedding blend can never disagree (same tensor, not two
independently-computed copies), and avoids a redundant `lgamma`/softmax pass.
The one subtlety: the mixture weight *used as input* at position `t`
describes token `t` itself, but the mixture weight *used as loss target* at
shifted position `t` must describe the token being predicted, i.e. position
`t+1` — so the target read is `outputs["mixture_weights"][:, 1:]`
(shift-aligned with `shift_labels`), while `forward()` internally used the
unshifted `w` (every position describing itself) to build `inputs_embeds`.
Since `forward()` already computes `w` for every numeric position in the
whole sequence (not just "input" positions), both reads come from one
tensor with no extra computation.

In `Loss.custom_loss`, this becomes a **third alternative base term**,
alongside the existing `label_weighted_loss`/`x_ent_loss` if/else:

```
if "basis_blended_tokens" in self.cfg:
    loss += self.basis_blended_token_loss(outputs, labels, **kwargs)
elif "label_weighted_loss" in self.cfg:
    loss += self.label_weighted_loss(outputs, labels)
else:
    loss += self.x_ent_loss(outputs, labels)
```

`quantile_token_loss`/`was_token_loss` remain unconditionally addable on top,
per the locked-in decision — see "Known gaps" for why that combination isn't
actually functional without further work.

**v1 scope note:** `label_weighted_loss`'s token-of-interest upweighting is
*not* folded into `basis_blended_token_loss` in v1 — the non-numeric branch
above uses plain unweighted CE even if `label_weighted_loss` is also
configured. Outcome tokens like `DSCG//expired` are typically non-numeric, so
this is a real gap if someone wants both; flagged under "Known gaps" as a
cheap follow-up (multiply `nonnum_loss`'s per-position terms by
`self.weights[shift_labels[~numeric]]` before summing) rather than built now.

## 8. `Extractor` changes

- **Model loading**: no code change (see 4.1 — Auto* registration handles
  it), *provided* `cotorra.basis_blended` gets imported before
  `AutoModelForCausalLM.from_pretrained` is called.
- **`collate_fn`**: mirror `Trainer.collate_fn`'s new logic — build
  `category_ids`/`ranks` from `exact_ranks_past` and the loaded model's own
  `raw_to_category`/`raw_to_collapsed` (read from `self.model.config`, *not*
  re-derived from `extraction.yaml`, since the collapsed vocab is fixed at
  train time — see next bullet). Both new tensors need the same
  `pad_sequence` treatment `input_ids` already gets
  (`extractor.py:60-64`), with pad values `-1` (category) and `0.0` (rank).
- **Column selection / init ordering**: `Loader` is constructed before the
  model in `Extractor.__init__` today (`extractor.py:44` before `:52`), but
  deciding whether to select the `exact_ranks_past` column ideally shouldn't
  need a fresh `extraction.yaml` flag that has to be kept in sync with the
  training config by hand (that's precisely the class of bug the
  `time_based_rope` "must match between training and extraction" gotcha in
  `CLAUDE.md` warns about). Recommended fix: reorder `Extractor.__init__` to
  build `self.model` first, then pass an explicit
  `basis_blended=hasattr(self.model.config, "categories")` flag into
  `Loader(...)`, rather than having `Loader` sniff its own `self.cfg` the way
  it does for `time_based_rope`. This means **no `basis_blended_tokens` key
  is needed in `extraction.yaml` at all** — a strict improvement over the
  `time_based_rope` pattern, made possible because this feature's config is
  fully self-describing once persisted in the model checkpoint. Worth
  double-checking with the user before implementing, since it's a slightly
  bigger structural change (constructor reordering + a new `Loader` param)
  than a minimal patch — flagged here rather than silently assumed.

## 9. `Tuner` / `TrainerDP` compatibility

- **`Tuner`**: no changes needed — it subclasses `Trainer`, calls
  `super().__init__()`, and reuses `self.trainer`/`self.model` as-is. The
  `reverse_lookup`/`bos_token_id` property refactor from §4.4 fixes its
  `summarize_trained_model` call for free.
- **`TrainerDP`**: same inheritance story for setup. The real open question
  is whether Opacus's `GradSampleModule` correctly computes per-sample
  gradients through our custom `forward()` (embedding gather + weighted sum
  via advanced indexing, rather than a registered nn.Module type Opacus has
  dedicated per-sample-grad hooks for, like a plain `nn.Embedding` lookup).
  Modern Opacus can generally handle arbitrary differentiable ops via its
  functorch-based grad sampler, but this needs **empirical validation**, not
  something resolvable by reading code. Treat DP support as best-effort/
  unvalidated in v1 — flagged under "Known gaps", not blocking the rest of
  the plan. If `log_alpha`/`log_beta` are trainable under DP, also worth
  watching whether per-sample-gradient clipping/noising disproportionately
  hurts them, since batches vary in how many numeric tokens (and which
  categories) they contain.

## 10. Config schema

New block, `training.yaml` only (see §8 for why `extraction.yaml` doesn't
need its own copy):

```yaml
basis_blended_tokens:
  k: !!int 8 # basis elements per numeric category
  train_beta_params: !!bool true # global toggle for log(alpha)/log(beta) grad
```

Composable with `time_based_rope` (both may be present simultaneously — the
doc requires this). Not composable in a currently-functional way with
`quantile_token_loss`/`was_token_loss` (no error raised, but see below).

## 11. Known gaps / open follow-ups

Flagging these explicitly rather than papering over them:

1. **`quantile_token_loss` + `basis_blended_tokens` doesn't actually work
   yet, despite no blocking error.** `quantile_token_loss`'s `self.vocab`/
   `self.label_to_cat`/`self.q_type` are built from `self.tkzr_cfg`
   (cocoa's *raw* vocab, e.g. 6641 tokens in `updated_absolute_centiles`),
   but under `basis_blended_tokens` the model's actual output vocab is the
   much smaller collapsed one — `outputs.logits`'s last dim won't match
   `self.label_to_cat`'s length, so enabling both today would index
   out-of-bounds or silently misalign, not gracefully coexist. Per the
   locked-in decision this isn't being guarded against or fixed now; if the
   combination is wanted later, `quantile_token_loss`'s vocab construction
   needs to be parameterized off the *collapsed* vocab (which happens to be
   easy, since collapsed-vocab labels reuse the `_Q<n>` suffix convention on
   purpose — see §3.3) instead of hardcoded to `self.tkzr_cfg.cfg.n_bins`.
2. **`label_weighted_loss` token-of-interest upweighting isn't combined with
   `basis_blended_token_loss`** in v1 (§7). Cheap to add later.
3. **DP (`train-private`) compatibility with the custom `forward()` is
   unvalidated** (§9) — needs an actual Opacus run to confirm, not just code
   review.
4. **`was_token_loss` stub is left broken** (calls an undefined method,
   `self.cfg.was_tokenLoss` typo) — explicitly out of scope per the locked-in
   decision, but it will keep being silently dead code (or crash) if anyone
   sets `was_token_loss:` in a config, regardless of `basis_blended_tokens`.
5. **`Extractor.__init__` reordering** (§8, model-before-loader) is proposed
   but not yet confirmed as wanted vs. a smaller patch that keeps a
   redundant marker key in `extraction.yaml`.

## 12. Numerical stability checklist

(Consolidating the stability-relevant notes scattered above into one place
for implementation time.)

- Clamp `ranks` to `[eps, 1-eps]` (suggest `eps=1e-4`, exposed as an optional
  advanced config key with that default, not required) before evaluating the
  Beta log-pdf — cocoa's `exact_rank` can legitimately be exactly `0.0` or
  `1.0` for a category's min/max training value.
- Compute mixture weights via `softmax(log_pdf, dim=-1)`, never
  `pdf / pdf.sum()` directly — avoids overflow when `alpha`/`beta` drift and
  density values get large, and avoids 0/0 if all k densities underflow.
- Use `lgamma` (or `torch.distributions.Beta.log_prob`, equivalent) for the
  Beta log-pdf rather than computing `Gamma(a)*Gamma(b)/Gamma(a+b)` directly.
- `log_alpha`/`log_beta` parameterization (rather than raw `alpha`/`beta`)
  already guarantees positivity via `exp()` with no extra clamping needed
  there.

## 13. Testing & validation plan

No pytest/CI in this repo (per `CLAUDE.md`) — validate the same way the rest
of the codebase does, via `if __name__ == "__main__"` self-checks plus real
runs:

1. **`basis_blended.py`'s own `__main__` block**: tiny synthetic vocab (2
   categories, k=4) —
   - confirm `log_alpha`/`log_beta` init matches the order-statistic formula
     exactly;
   - confirm mixture weights sum to 1.0 for a batch of random ranks;
   - confirm `log_alpha.grad`/`log_beta.grad` are populated after a backward
     pass when `train_beta_params=True`, and `None`/zero when `False`;
   - `save_pretrained`/`from_pretrained` round-trip: reload and assert
     config fields and `state_dict()` match bit-for-bit.
2. **End-to-end smoke test** against `~/new_cocoa/cocoa/updated_absolute_centiles`
   (already has `exact_ranks`): `cotorra train` with `llama_32_mid` preset +
   `training_args.max_steps: 10` (already a commented-out knob in
   `training.yaml`) → confirm it runs to completion, loss is finite and
   decreasing, then `cotorra extract` on the resulting checkpoint → confirm
   hidden states come out finite.
3. **Independent numeric check**: for one hand-picked `(category, rank)`,
   compute `w` via a from-scratch numpy/scipy Beta-pdf calculation and
   compare against the model's internal value for equality — regression-test
   the math itself, not just "it runs."
